## 524 策略纠正

仅凭 HTTP 524 不能判断 Resin 节点故障；之前换节点没有足够的有效性证据。
现在 failover 的 524 日志不进入恢复队列，旧 pending 事件也不会补执行。
resolver 拒绝旧 524 信号，最终事件入口在访问租约前拒绝 `upstream_524` 或 HTTP 524，
包括被误标为 `transport_timeout` 的反馈。524 仍可在业务层原始日志中观察。

独立拨号、TLS、连接故障和已有缺终止事件恢复保持原行为；本次没有改动 Router/Sub2API
的上游重试或账号调度，也没有测试或恢复 Astra 账号。Resin 通用的保留连接 API 继续保留。

## 保证范围与历史纠正

当前无限排空路径的核心代码审查和真实网络测试没有发现连接中断的发布阻断项。
正常更新必须用 `resin-bluegreen-deploy.sh deploy <immutable-digest>`：新槽健康后接新连接，
旧槽只停止接受连接，等待现有连接结束；下游地址和配置无需变更。

两个槽不是两套实时复制的数据库。快照到切流期间须暂停人工控制面修改，maintenance 与
部署共用数据锁；旧槽后续 lease/cache 状态不会合并。启用自定义 endpoint 会因端口冲突
风险被拒绝部署。旧槽长期不排空时拒绝复用，不能靠强杀来维持“无损”承诺。
有限 drain timeout、直接 Docker/Compose 停启、Docker daemon/主机重启及外部上游故障
不在无中断保证内。`cmd/resin` race 覆盖已有本地历史验证，但现有 Resin CI race job
仅覆盖 proxy/routing，这是剩余自动化覆盖缺口。

部署器的独立只读审查再次核对了事务、隔离、回滚、锁和精确容器标识，未发现当前路径的
发布阻断项。剩余运行边界：legacy 停止命令的 CLI 等待上限为 30 秒，超时会报错后由 timer
继续协调，不会强杀容器；`start`/`reconcile` 的 systemd 启动上限为 120 秒，极端缓慢恢复
可能超时重试。正常 `deploy` 须由宿主 root 直接执行，当前 unit 未授予 `nsenter -n` 权限。
NAT 已切换但事务尚未提交时崩溃会保守回切，候选随后排空，不保证该次升级继续完成。

旧结论“顶层 200 即成功、524 已被完全挡住”不成立：09-13 01:44:41 至约 02:24 的

但精确 SSE 分类仍有 7 次 524 型失败和 1 次等待响应头超时。文本搜索命中的第 9 条
`response.failed` 只是正文引用，实际 completed。这个历史窗口不能证明今天所有上游错误清零。
400 的 provider-state 修复属于 Router，524 自动换节点及其连带 502 属于 Guard/Resin；
双槽处理 Resin 更新中断，各层职责不能混为一谈。
