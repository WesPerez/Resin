# 2026-07-25 V2Ray 443 间歇性卡顿审查

> 历史事故证据，不是当前部署说明。文中的旧 CN fallback 服务和任务已退役，不得据此恢复或配置；
> 当前代理拓扑以本文“当前部署和本次优化”以及 `docs/inventory.md` 为准。Resin 只负责其他应用的出站数据面。

> 当前部署（2026-09-03）：公网订阅入口为共享 Nginx `:443`，分别转发到
> `xray-proxy.service:12762`（WS 回退）和 `:12763`（XHTTP H2 主节点）。TLS 在 Nginx 终止；
> 旧 `v2ray-stable-ws`、KCP 和 `10810` 服务均已退役。

## 结论摘要

当前症状不是“服务器挂了”或“代理池满了”，核心问题集中在公网入口建连阶段：

1. 公网客户端到 `weesai.com:443` 的跨网 TCP/TLS/WS 建连存在高 RTT、重传和间歇性超时。客户端日志中的 `websocket ... wsarecv` 发生在客户端到入口的连接阶段；这类连接有的能完成，有的在服务端收到完整请求前就卡住，因此服务端不会产生 503。
2. 每个浏览器会建立许多彼此独立的目标连接；当前 VLESS-WS 节点没有从服务端强制把这些连接合并。某些 WS 成功、另一些 WS 卡住时，就会出现同一时刻不同浏览器或不同标签页表现不一致。

因此，“同一时刻一个浏览器能用、另一个像没网”并不矛盾：它只能证明部分独立隧道成功，不能证明这一分钟里的所有新隧道都稳定。

## 当前部署和本次优化

```text
客户端 Mihomo/Clash
  -> TLS + HTTP/2 :443
  -> Nginx
       -> grpc_pass 127.0.0.1:12763 -> Xray VLESS/XHTTP stream-up（主）
       -> proxy_pass 127.0.0.1:12762 -> Xray VLESS/WebSocket（回退）
```

当前订阅把 XHTTP 放在原 WS 节点名的位置，并保留带 `-ws` 后缀的回退节点，因此刷新订阅后旧选择通常会迁移到 XHTTP；客户端仍可手动切回 WS。XHTTP 主节点的目标是减少 TLS/HTTP 升级和短连接重建，不是改变美国源站的物理 RTT。

## 历史链路和职责

```text
客户端/浏览器
  -> DNS、TCP、TLS、WebSocket（公网 :443）
  -> Nginx :443
  -> VLESS-WebSocket 127.0.0.1:12761（历史）
  -> V2Ray direct/dns-security/blocked
  -> 目标站
```

事件发生时，本机 `v2ray`、`v2ray-grok-pool` 和 `egress-fallback-proxy` 属于服务端出站能力，不是公网
443 入站的故障转移入口。后两者已于 2026-08-06 退役；该历史事实不能作为当前恢复步骤。它们也不能修复
客户端尚未连到 `weesai.com:443` 的情况。

## 事实证据

### 入口状态（约 16:12--17:12，东八区）

- Nginx、`v2ray-stable-ws`、443 listener 和 `127.0.0.1:12761` 均正常。
- Nginx WS access 记录约 1.4--1.6 千条，已完成的请求全部为 `101`；`503=0`、`429=0`。
- error log 没有新的 `limit_conn` 或 `limit_req` 事件。
- 已完成 WS 中约 210 条小于 1 秒，约 491 条小于 5 秒；在几个峰值分钟，短会话占比约 40%--60%。
- 单一来源在峰值时约占 87%--99% 的会话；`max_peer_443_est` 最高约 92，总 `conn_443_est` 最高约 115。

### 当前 XHTTP 观察窗口（2026-09-03）

- `xray-proxy.service`、Nginx、`12762` 和 `12763` 均为 active/listening，XHTTP access 以 `200` 为主，未见持续的 5xx/499 峰值。
- Nginx 到 `127.0.0.1:12763` 的 `upstream_connect_time` 约为 0--2 ms，说明本机反代没有形成主要排队；长请求持续数十到数百秒是 XHTTP 流式会话的正常表现。
- Xray access log 已关闭，Nginx XHTTP 日志不记录完整随机路径。主机级 TCP 重传/超时仍会间歇告警，需和其他 Docker/数据库/构建任务区分。
- Mihomo `1.19.29` 存在公开的长时间 XHTTP CPU 异常报告；客户端应升级到 `1.19.30` 或更新版本后再评价长期稳定性。

### 用户给出的 15:39--15:40 窗口

健康任务历史样本显示，`15:39` 的 `conn_443_est` 约 45，随后增至约 291，再到约 508；对应 `conn_12761_est` 只有约 21、15、15，同一窗口已完成 WS 只有个位数到十几条，`503=0`。结合客户端同刻的大量 `wsarecv`，说明绝大多数 TCP 连接停留在 TLS/HTTP/WS 请求尚未完整到达后端的阶段，不能用 location 层的 `limit_conn` 统计解释。由于公网 443 还承载其他虚拟主机，不能只凭两项连接数做绝对等式；但单 peer 聚集、时间戳和客户端日志三者一致，使该判断置信度较高。

### TCP 和资源

- 远端 443 连接 RTT 约 150--360 ms，部分连接有重排和重传。
- 历史 TCP 重传和超时偏高，但当前不是全机 listen backlog 或 conntrack 耗尽：`nf_conntrack_count` 约 485、上限 65536，近期 `ListenOverflows=0`。
- BBR 已启用；`worker_connections=4096`，`LimitNOFILE` 远高于当前连接量。
- 本机 nftables/iptables 没有针对 443 的 `connlimit`、`hashlimit` 或新建连接速率限制；Fail2ban 两个 jail 当前封禁数均为 0，当前主要 peer 也未命中静态拒绝规则。
- Swap 已使用约 3.6--3.8 GB，健康任务持续告警；实时 `vmstat` 只有间歇性 swap-in，内存 PSI 的 `full` 为 0。因此这是需要单独治理的资源风险，但没有证据证明它是本次 WS 部分连接超时的唯一根因。
- Nginx 有 3 个旧 worker 处于 `shutting down`，其中仍持有约 24 条公网 443 ESTAB；一个已持续约 9 小时。这是长连接回收问题和资源风险，不是当前 503 的证据。

### V2Ray 和出站池

- 近 30--60 分钟 `v2ray-stable-ws` 没有重启，也没有典型的目标拨号、TLS、`freedom` timeout/refused 错误。
- 主要异常是 WS 已建立后客户端很快发送正常关闭（`close 1000`），极少量 `close 1006/unexpected EOF`，以及少量被取消的 DoH 查询。
- 近 90 分钟对 272 次 `blocked` 做 geosite 精确匹配后，约 96% 来自广告规则，`category-doh`/`category-httpdns-cn` 实际命中为 0；因此 DoH 黑洞规则不是本次浏览器差异的现有证据。
- `egress-fallback-proxy` 近一小时 `active/queued` 均未打满，`pool_exhausted`、队列满、CONNECT timeout 和新增最终失败均为 0。

## 分层判断

### 已排除或置信度高

- **不是当前窗口的 `limit_conn`/`limit_req` 打满**：高置信度。历史旧值为单 IP 32，曾出现限流；提高到 384/全局 768 后，本窗口无 503 和限流日志。
- **不是当前出站代理池容量耗尽**：高置信度。池的队列和失败计数没有增长。
- **不是服务端普遍无法访问目标站**：中高置信度。当前窗口没有目标拨号失败模式。
- **存在客户端建连风暴与公网路径抖动**：高置信度。大量单客户端并发、短 WS、150--360 ms RTT、重传/超时和客户端 `wsarecv` 相互吻合。

### 仍需区分

- 运营商/跨境路径丢包、用户本地 Wi-Fi/路由器丢包，还是域名/IP 被选择性干扰，当前仅凭服务端日志不能定责。需要失败时刻的客户端网络统计或从多个网络的合成探针。
- 少数具体资源是否被广告规则误伤，需要失败域名与路由日志对齐；它不能解释客户端到 `weesai.com:443` 本身的 `wsarecv` 超时。

## 已执行的改动及效果

1. Nginx WS 入口的 per-IP `limit_conn` 从历史 32 调整为 384，全局上限 768；握手增加 100 r/s、burst 60；反代连接超时为 10 秒。
2. 新增 Xray VLESS/XHTTP `stream-up` 入站 `127.0.0.1:12763`，Nginx 443 启用 HTTP/2 并用 `grpc_pass` 转发；WS 入站 `127.0.0.1:12762` 保留为回退。
3. 订阅生成器同步 XHTTP/WS 入口参数，并在生成前校验两入站 UUID、网络类型、`stream-up`、端口和随机路径，避免后续生成回写旧值。
4. 新增 `xray-proxy-health` 每分钟任务，记录 TLS、WS/XHTTP 状态码、短会话、并发 peer、内存、swap、TCP 重传/超时/监听丢弃；timer 当前 `enabled + active`。
5. 修正健康任务中 TCP 计数和 peer 列解析错误，并通过离线测试。
6. 本次审查后新增 `ws_101_short_ratio`、`conn_443_backend_gap` 和 `pre_ws_stall_candidate`，用于把短连接风暴与“公网 443 已建立、后端未同步增长”的候选前置卡顿直接记录下来；无需重启代理服务。

效果是：历史的 32 连接限流已不再主导当前窗口，XHTTP 主链路减少了客户端握手和连接 churn，入口可观测性显著提高；但这些改动不能改变客户端到单一美国源站 IP 的公网路径，也不能保证旧版客户端不重建连接，所以没有根治跨网丢包或物理 RTT。

## 关于 DoH 规则

当时历史运行的 `/etc/v2ray/stable-ws.json` 中，blocked 域名集合包含：

- `category-ads-all`
- `category-public-tracker`
- `category-doh`
- `category-httpdns-cn`

前两类属于策略拦截；后两类理论上可能影响浏览器或应用的解析通道，但本次窗口实际命中为 0。当前没有证据支持为此重启正在承载长连接的后端，因此未修改生产配置。后续只有在失败域名明确命中 DoH/HTTPDNS 时，才将其从 `blocked` 拆出并单独验收。

## 真正有效的方案排序

### 立即可做、无需第二 VPS

- 保留现有 443 入口和监控；对失败域名做路由命中核对，只有确认误伤时才调整广告或 DoH 规则。
- 已增加短 WS 比例和单 peer/后端差值组合告警；旧 worker 存活时长仍保留为后续指标，避免当前继续 reload 制造更多旧连接。
- 清理内存和长期 swap 属于独立运维事项，必须先定位高占用进程并有回滚窗口，不能通过反复重启 V2Ray 代替。

### 真正降低连接风暴（需要客户端订阅/配置变化）

- 当前已提供 XHTTP H2 主节点和 WS 回退；客户端必须刷新订阅并使用 Mihomo `1.19.30+` 才能实际获得该变化。不要再叠加通用 `smux`，XHTTP 自带 XMUX。
- 若 XHTTP 真实流量稳定，保持 `select` 组；不要用容易误报的 URLTest 结果自动淘汰 XHTTP。若客户端 CPU 或真实断流异常，手动切回 WS 并保留指标。

### 真正增加故障域（客户端可保持同域名时）

- 增加香港/日本等独立线路的 TCP/SNI 透传边缘，或使用合规的全球加速/Anycast，再由 DNS 健康切换。现有单机出站池不能充当这个入口。
- CDN WebSocket 不应未经条款、长连接空闲超时和回源质量验证就作为生产主路径。
