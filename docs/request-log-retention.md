# 请求日志保留

请求日志保留现有容量与分片数量上限，并在原生写入循环每五分钟执行维护，无新宿主清理器。
活动分片创建满三天后正常关闭并轮转，关闭分片在最后落盘后三天淘汰。
因此正常时钟及正常维护下，新产生的请求日志最长约六天加两个维护间隔；晚结束的请求从实际落盘开始计算，
不按请求开始时间误删。低流量和空队列也会运行维护。

活动数据库、在读分片、关闭失败、异常/未来时间和变化中的文件受到保护。
数据锁覆盖查询连接关闭和原生删除，读取屏障在取锁前执行，避免与单写入循环死锁。
每个分片用一行 `request_log_retention` 记录最后请求落盘时间，与日志同事务更新。
旧分片在第一次结构维护之前，以 DB/WAL/SHM 的最大有效修改时间初始化这一行；
以后重启、索引维护或 SQLite checkpoint 均不刷新它，维护也不扫描请求表。
旧版已经超期的关闭分片可在首次维护淘汰。异常时钟、关闭失败和身份变化会延迟清理并报告，
因此保留期限与数量是正常运行目标，不能绕过保护强行满足。
容量仍沿用原来的分片数量淘汰规则，可早于三天淘汰最旧关闭分片。
此目录延续应用单写入者所有权，不能让另一实例同时写同一日志目录。
状态、缓存、凭据与租约不属于此策略。该职责最初基于实际运行 40f520 构建，现已适配到最新上游 mine；
当前生产首跳缺少原生停写/最终落盘屏障及已登记在线交接配置，正式发布须先完成既有
发布协议，不能用候选 CI 成功或 socket 排空代替数据交接。
